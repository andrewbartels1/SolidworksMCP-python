## Context

- The docs are MkDocs Material. `mkdocs.yml` has `site_url`
  (`https://andrewbartels1.github.io/SolidworksMCP-python`), `repo_url`,
  `site_name`, `site_description` and a hand-kept `nav` of about 60 pages
  in six sections, plus `API Reference: api/` (generated by
  `docs/gen_ref_pages.py`, not Markdown in `docs/`). Directory URLs are on,
  so `user-guide/tools-overview.md` is served at
  `<site_url>/user-guide/tools-overview/`.
- `mkdocs.yml` uses `!!python/name:` tags (superfences, emoji), so a plain
  `yaml.safe_load` refuses it.
- Headings get ids from Python-Markdown's `toc` extension with its default
  slugify, plus explicit `{#id}` attributes (`docs/demos.md` uses them).
- The README and docs hold 116 different URLs today. Most are
  `github.com/andrewbartels1/...` and the docs site; the rest are
  third-party (python.org, astral.sh, shields.io badges, ollama.com, …).
  Example addresses (`http://127.0.0.1:11434`, `http://YOUR-WINDOWS-IP:8000`,
  `http://my-gpu-server:11434`) appear in code blocks.
- No page declares a `description:` in front matter. Most open with
  `# Title` and a paragraph; some open with a list, a blockquote or a
  "Last updated" line instead (`docs/index.md` opens with a feedback
  blockquote and badges; `docs/planning/roadmap.md` with
  "**Last updated:** …").
- Neither `pyyaml` nor `markdown` is a runtime dependency; both come with
  the `docs` extra (mkdocs). `httpx` is a runtime dependency.
- `src/solidworks_mcp/progress/` is the pattern to follow: a generator in
  the package, run with `python -m`, a test that fails when its output is
  stale.

## Goals / Non-Goals

**Goals:**

- `llms.txt` with nothing hand-written: every title and summary traceable
  to one page, word for word.
- Every link checked: within the project offline in the unit tests, and
  every external URL online, with a full report.
- A file a security reviewer can read in a minute and trust: our URLs
  only, no hidden characters, no HTML.

**Non-Goals:**

- `llms-full.txt` (every page's full text). Not asked for; the pages are
  one click away.
- Front-matter `description:` fields. A summary that lives only in front
  matter is invisible on the page and can drift from what the page says,
  which is the problem this change exists to remove.
- Checking links in `openspec/`, `CHANGELOG.md`, source docstrings or the
  skill's reference files. They aren't published as the docs site. (The
  skill could come later as its own item.)
- Anything taken from PR #225.

## Decisions

### 1. One package, `solidworks_mcp.doc_links`, three modules and a CLI

- `pages.py`: reads `mkdocs.yml` (a `SafeLoader` subclass that turns any
  `!!python/...` tag into `None`), walks `nav`, and for each page returns
  its nav section, URL, `# ` title, opening paragraph and heading ids.
- `llms_txt.py`: builds the text of `llms.txt` from the pages, and checks
  a given text against it (staleness, word-for-word, allowed URLs, line
  shapes, forbidden characters).
- `links.py`: finds links in Markdown (outside code), resolves internal
  ones against `docs/` and the heading ids, and checks external ones
  online.
- `__main__.py`: `python -m solidworks_mcp.doc_links build` writes
  `docs/llms.txt`; `check` runs the offline checks; `check-external`
  runs the online check and writes the report. Exit code 1 on any
  failure; output through loguru.

Alternatives: a script under `src/utils/` (not covered by the coverage
rule or the test layout); an off-the-shelf link checker such as `lychee`
or `mkdocs-htmlproofer-plugin` (one more third-party tool in the docs
pipeline, the thing this item is wary of; and neither does the
word-for-word check). The checks are small enough to own.

### 2. The summary is the page's first prose paragraph

The title is the page's `# ` heading; the summary is the first paragraph
after it that is prose (not a blockquote, `!!!` admonition, list, table,
fenced code, image or badge line, or HTML), stopping at the first `## `.
Links become their text (`[uv](https://…)` → `uv`), other Markdown is kept
as written, and line breaks inside the paragraph become single spaces.

Pages that open badly (a "Last updated" line, a sentence ending in a
colon before a list) are fixed **in the page**, by giving it a real
opening paragraph, never by writing text into `llms.txt`. Task 4 reviews
every generated entry for this.

### 3. Sections follow the nav

Top-level pages (Home, Demos, Progress, Compatibility) go under
`## Overview`, first. Then one `## ` per nav section, its pages in nav
order; a nested section's pages are listed under their top-level section.
`API Reference: api/` is left out (it's generated Python reference, and
not a Markdown page in `docs/`). The file is `docs/llms.txt`, so MkDocs
copies it to the site root unchanged.

### 4. What the file may contain

- URLs: only under `site_url` or `repo_url`. Entries link to the page's
  published URL.
- Characters: no Unicode category `Cf` (format: zero-width, BOM, bidi
  controls) or `Cc` (control) other than `\n`; no `<` that starts a tag or
  comment.
- Lines: one of `# …`, `> …`, `## …`, `- [title](url): summary`, blank.

The builder refuses to produce a file that breaks these, naming the page;
the checker refuses a committed file that breaks them, naming the line.
The same rules on both sides mean a hand edit can't sneak past the
checker by matching a bad build.

### 5. Offline link check in the unit tests

An integration test runs the offline check on the real README and docs
and asserts no failures, the way the progress test does. Unit tests feed
the checker small Markdown strings. Internal links: relative paths
resolved from the linking page; links to `site_url/...` mapped back to a
page in `docs/`; files that aren't Markdown (images, GIFs) just need to
exist. README links are resolved from the repo root (they point at
`docs/...` paths or the site).

Anchors: the ids Python-Markdown's `toc` would give (its default
slugify: NFKD-normalise, drop non-word characters, lowercase, spaces and
hyphens to one hyphen, deduplicated with `_1`, `_2` in page order), plus
`{#id}` attributes. The slugify is written in the package (a few lines)
so `markdown` isn't needed at runtime; a unit test checks it against
`markdown.extensions.toc.slugify` on every heading in the docs, skipped
when `markdown` isn't installed.

### 6. Online check: GET, same host, retry, report

- One `GET` per unique URL (some sites refuse `HEAD`), following
  redirects, 15 s timeout, a plain `User-Agent` naming the project (no
  personal details), up to 8 at a time.
- Pass: final status 2xx, and the redirects stayed on the same site: the
  same host (`www.` ignored), a subdomain either way, or a host listed in
  `SAME_SITE` with a reason. (Changed after the first run, below.)
- GitHub issue and pull request links are checked through
  `api.github.com/repos/<owner>/<repo>/issues/<n>`, with the CI token when
  one is set; the pages answer 429 to scripts. At most two requests at
  once per host.
- Retry twice on timeouts, connection resets and 429/5xx, with a short
  back-off; a 4xx other than 429, or a host that doesn't resolve, fails
  at once.
- A small allow-list in the package for sites known to refuse robots
  (answering 403 to any script) would hide real failures, so there is
  none to start with; if one turns up, it's added with a reason, and the
  report still lists it as "not checked: <reason>".
- The report is Markdown at `tests/.generated/link-report.md`: a summary
  count, then a table of every URL, its result (status, or where it
  redirected), and each `file:line` it appears on. In CI it is uploaded
  as a workflow artifact and its failures printed to the log.

### 7. Where the online check runs

A new job in `deploy-docs.yml` after `deploy` (so `llms.txt` and new
pages are live before they're checked), and a weekly `schedule` trigger
(Mondays 06:00 UTC) that runs only that job. It is not in `make test` or
`dev-test`: the unit tests stay offline. `dev-commands.ps1 dev-links`
and `make links` run it by hand.

### 8. `pyyaml` in the test and dev extras

The package imports `yaml` at module level. `pyyaml` is added to the
`dev` and `test` extras (the `docs` extra already has it through
mkdocs). The server never imports `doc_links`, so no runtime dependency
is added.

### 9. Security review and the first runs (2026-11-15)

**The file.** 54 entries in six sections (Overview 4, Getting Started 11,
MCP Server Guide 8, Tool Catalog 15, Agents and Skills 14, Planning 2).
Every URL is under `site_url`; the checker proves it on every test run.
No HTML, no comments, no control or format characters. Every line was
read by hand:

- Ten pages opened badly and were fixed in the page: the home page (a
  bold tagline), the VS Code setup (no opening at all), the U-Joint
  prompts (a "**Note:**"), integration testing, worked examples, SoC and
  the sample models guide (sentences ending in a colon), the agent skill,
  the roadmap and the API coverage map ("Last updated" lines first).
- The local-LLM page's opening carried `http://127.0.0.1:11434/v1`; the
  address moved to the page's second paragraph, so the strict URL rule
  stands.
- The COM pitfalls page opened with "If you are an AI coding assistant
  … read this page before touching any COM-related code", an instruction
  to agents. It's ours and harmless, but `llms.txt` should describe, not
  instruct, so that sentence moved to the second paragraph.
- No summary now addresses the reader as an agent or tells it to do
  anything.

**Offline run.** 402 links (219 relative) in the README, 60-odd pages and
`llms.txt`: no broken page, file or anchor.

**First online run.** 145 URLs. Findings and what changed:

- Every `andrewbartels1.github.io/SolidworksMCP-python/...` URL redirects
  to `andrewbartels1.com/SolidworksMCP-python/...`, the custom domain set
  on the owner's GitHub Pages site. Only the account owner can set that,
  The owner chose (2026-11-15) to point every link at
  `https://andrewbartels1.com/SolidworksMCP-python/` directly: `site_url`,
  the READMEs and the docs home page now use it, and the redirect is not
  allowed as the same site.
- `codecov.io` sends the badge link to `app.codecov.io`: subdomains now
  count as the same site.
- `console.anthropic.com/settings/keys` now redirects to
  `platform.claude.com`: the link was updated.
- 22 GitHub issue pages answered 429: they are now checked through the
  API (above).
- `towardsdatascience.com` answers 403 to scripts and `www.solidworks.com`
  never answers one; both are in `NOT_CHECKED` with the reason. The
  checker does not pretend to be a browser to get past them.

After those changes: 145 URLs, 143 visited and passing, 2 not checked.

## Risks / Trade-offs

- **Some sites refuse scripts** (403/429 to anything without a browser
  `User-Agent`), so the weekly run may fail on a link that works in a
  browser → the report says which; we fix the link, switch it to a page
  that answers, or add it to the allow-list with a reason (Decision 6).
- **Links break between runs** (a site moves a page midweek) → the
  weekly run catches it within a week; the deploy run on every merge to
  `main` catches it sooner.
- **The deploy job fails after the site is live** → it doesn't undo the
  deploy, it flags a link to fix. That's the intent: a third-party page
  moving shouldn't block publishing our docs.
- **Word-for-word means page edits move `llms.txt`** → the stale-file
  test says which command rebuilds it, as the progress test does.
- **Our slugify drifts from Python-Markdown's** → the parity test over
  every docs heading catches it wherever `markdown` is installed (CI).
